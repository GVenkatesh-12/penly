# ADR-003 — Compose + Native Performance Canvas

- **Status:** Accepted
- **Date:** 2026-08-14
- **Source:** [plan.md §4, §15](../plan.md#15-canvas-architecture)

## Context

Penly needs modern, adaptive UI (phones, tablets, dark mode, accessibility) while the ink surface must hit < 20 ms active-stroke latency with no UI jank. A pure-Compose canvas risks recomposition and node churn on the highest-frequency path; a pure-View app sacrifices modern UI ergonomics.

## Decision

Use a **hybrid approach**:

- **Jetpack Compose** (Material 3 foundation + custom design system) for all application UI.
- **Native Android View/rendering primitives** for the performance-critical ink surface (the `EditorSurface` and its render layers).

Keep the two worlds apart through the editor coordinator boundary. Core modules never know about either UI framework ([plan §7](../plan.md#7-module-structure)).

## Consequences

### Positive

- Best of both: modern adaptive UI and a low-latency, allocation-conscious ink path.
- The document/ink model stays UI-framework-agnostic, keeping the door open for KMP.

### Negative

- Two UI stacks to learn and test (Compose UI tests + View-layer tests).
- Interop seams (AndroidView / ComposeView) need disciplined ownership to avoid leaks.

### Neutral

- "UI never wins over pen latency" principle ([plan §1](../plan.md#1-product-thesis)) is enforced structurally: the ink surface is not hostage to Compose recomposition.
