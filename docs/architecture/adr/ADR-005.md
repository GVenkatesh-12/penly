# ADR-005 — Room + File Store Split

- **Status:** Accepted
- **Date:** 2026-08-14
- **Source:** [plan.md §11–12](../plan.md#11-database-schema)

## Context

Handwriting pages contain large binary payloads (stroke batches, images, PDFs, thumbnails). Storing them all in SQLite bloats the database, slows queries, complicates backups, and makes maintenance (integrity checks, regeneration) awkward. Storing all metadata in files makes transactions, indexes, and search painful.

## Decision

**Split storage into two layers:**

- **Room + SQLite** stores metadata, indexes, and transactional state: workspaces, notebooks, sections, documents, pages, object metadata (with bounding boxes), tags, revisions, journal entries, sync state, settings.
- **File store** (`ContentStore`) stores large/opaque payloads: page payloads, assets, thumbnails, exports, journal, recovery files.

The `ContentStore` abstraction (`put/open/move/delete/exists/checksum`) is the only way code touches file paths — direct path construction is banned.

## Consequences

### Positive

- Database stays small and fast; spatial queries and FTS5 later work on metadata.
- Files can be integrity-checked, cached, and migrated independently.
- Storage backends can be swapped later behind `ContentStore`.

### Negative

- Two-layer consistency is required: object metadata (Room) must reference payload files (File Store) coherently; recovery/repair must handle both.

### Neutral

- This split is what makes future features (search, sync, backup) cheap to add.
- Room schema still holds object bounding boxes (`min_x`, `min_y`, `max_x`, `max_y`) for future spatial indexing without decoding strokes.
