# ADR-012 — Experimental Dependency Isolation

- **Status:** Accepted
- **Date:** 2026-08-14
- **Source:** [plan.md §5, §48](../plan.md#5-dependency-policy)

## Context

The Android ecosystem moves fast: AndroidX Ink 1.1 is alpha, Compose evolves, PDF engines vary. Penly's persisted documents must be openable five years later ([plan §71](../plan.md#71-final-engineering-principle)). A dependency upgrade must never be able to redefine the app's public persisted behavior.

## Decision

**Experimental dependencies are isolated behind interfaces/adapters; the persisted format depends only on stable, owned representations.**

Adapters required around:

- AndroidX Ink (`InkAdapter`: `DocumentInk ↕ InkAdapter ↕ AndroidX Ink`)
- PDF engine (`PdfDocumentSource`, `PdfPageRenderer`, `PdfAnnotationLayer`, `PdfExporter`)
- Image decoding
- Storage implementation (`ContentStore`)

If AndroidX Ink changes in a later release, `InkAdapter v1 → Ink API current` upgrades independently of the document schema.

Dependency policy rules ([plan §5](../plan.md#5-dependency-policy)):

1. Never use an alpha dependency in the hot path merely because it has a desirable feature.
2. Experimental dependencies must be isolated behind an interface/adapter.
3. Every dependency needs an owner module and a reason to exist.
4. Prefer official AndroidX/Kotlin libraries for foundational platform behavior.
5. Do not add a library for functionality requiring fewer than roughly 100 lines of clear, well-tested code unless it solves a difficult platform compatibility problem.
6. Pin versions centrally (`gradle/libs.versions.toml`).
7. Use dependency locking/verification where practical.
8. Review release notes before upgrades.
9. Upgrade one foundation family at a time when possible.
10. Every persistence dependency upgrade must run migration and recovery tests.

## Consequences

### Positive

- Dependency upgrades become routine, testable events instead of format-breaking risks.
- Users' documents are insulated from ecosystem churn.

### Negative

- Adapter layers add indirection and a small amount of boilerplate.
- Requires discipline: leaking a third-party type through a domain interface is a review-blocking violation.

### Neutral

- This is the key reason `androidx.ink.*` types must not appear in every business-layer class ([plan §48](../plan.md#48-upgrade-compatibility)).
