# ADR-006 — Versioned Native Document Format

- **Status:** Accepted
- **Date:** 2026-08-14
- **Source:** [plan.md §10](../plan.md#10-document-format)

## Context

Users must be able to export their work and open it years later. Unversioned or undocumented formats turn an app into a data jail. The plan requires: open format, exportable, versioned, forward-compatible.

## Decision

Introduce a **versioned native package format** immediately, with the logical format as a specification, independent of physical packaging.

- Suggested extension: `.penly` (container may later change to ZIP/container storage without changing the logical document specification).
- Package layout:

```text
note.penly/
├── manifest.json
├── document.json
├── pages/
│   ├── page-01.bin
│   └── page-02.bin
├── assets/
│   ├── image-001.webp
│   └── attachment-001.pdf
└── thumbnails/
    ├── page-01.webp
    └── page-02.webp
```

- Manifest carries `format`, `formatVersion`, `minimumReaderVersion`, `documentId`, `createdAt`, `updatedAt`.
- **Compatibility rules:** every format version defines a minimum reader version, optional writer capabilities, migration strategy, unsupported-object behavior, and integrity checking.
- **Unknown fields:** readers ignore unknown optional metadata (forward-compatible metadata additions).
- **Unknown object types:** readers preserve unknown objects as opaque payloads where practical and show a compatibility notice only when editing is impossible. A newer object type must never corrupt the whole document.

## Consequences

### Positive

- User data is portable, documented, and forward-compatible.
- Migrations are explicit and testable.
- The format spec (`docs/document-format/format-spec.md`) is the contract for compatibility.

### Negative

- Format design must be careful up front; changing the spec later is expensive.

### Neutral

- The `.paperforge` name in the plan was superseded by the project name **Penly** (extension `.penly`); the format versioning rules are unchanged.
