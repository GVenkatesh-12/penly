# ADR-007 — Command-Based Undo/Redo

- **Status:** Accepted
- **Date:** 2026-08-14
- **Source:** [plan.md §14](../plan.md#14-undo-redo-architecture)

## Context

Undo/redo must be deterministic and fast (< 50 ms targets) and must not blow up memory on large documents. Bitmap snapshotting is banned, and undo must eventually map to revision history and sync.

## Decision

Implement undo/redo with **commands**:

```text
AddObject, DeleteObject, UpdateObject, MoveObjects,
TransformObjects, ChangeBrush, InsertImage, InsertText
```

Each command has `execute()`, `undo()`, `serialize()`.

The history layer exposes `canUndo`, `canRedo`, `undo()`, `redo()`.

**Memory strategy:** command records plus periodic state checkpoints for very large documents, never unlimited raw snapshots:

```text
Commands → Checkpoint → Commands → Checkpoint
```

This design maps naturally to revision history and sync later.

## Consequences

### Positive

- Fast, deterministic undo/redo with bounded memory.
- Commands serialize → journal/recovery and future revision history reuse the same records.

### Negative

- Every mutating operation must be a command; sloppy mutations break the model.
- Checkpointing requires careful state invalidation design.

### Neutral

- Undo/redo is tested with property tests (state → ops → undo all ≈ initial state, [plan §50](../plan.md#50-property-based-testing-candidates)).
