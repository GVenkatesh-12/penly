# ADR-008 — Journal/Recovery Strategy

- **Status:** Accepted
- **Date:** 2026-08-14
- **Source:** [plan.md §13, §44](../plan.md#13-crash-safe-write-pipeline)

## Context

A handwriting app must assume crashes and power loss can happen at any point — including mid-stroke, mid-save, or right after writing. The v0.1 definition of done requires crash recovery and no known data-loss bugs.

## Decision

Use a **journal + recovery** strategy:

```text
Stylus event → In-memory editor state → Command
   → Journal append → Async durable commit → Document state
```

- The UI never waits for disk I/O per input point.
- During a stroke: keep the active stroke in memory, render immediately, **no database row per point**.
- On stroke completion: convert to immutable stroke data, append one logical command/journal record, persist asynchronously, update page revision, schedule thumbnail regeneration.

Startup recovery:

```text
open document → check journal → replay incomplete operations
   → validate content references → repair if possible → open document
```

**Never delete the journal before the corresponding durable state is known to be valid.**

## Consequences

### Positive

- Committed content survives crashes and power loss (verified by fault-injection tests, [plan §55 Phase 4](../plan.md#phase-4--crash-safety)).
- Autosave is invisible; save state UI (`Saved`/`Saving…`/`Recovered`) is truthful.

### Negative

- Journal management adds storage and code complexity.
- Recovery replay must be idempotent and fast at startup.

### Neutral

- On app termination/backgrounding: flush pending durable work, persist editor checkpoint when necessary, maintain recovery data if clean flush is impossible ([plan §44](../plan.md#44-save-semantics)).
