# ADR-016 — AI Provider Abstraction (On-Device + BYOK)

- **Status:** Accepted
- **Date:** 2026-08-19
- **Source:** [plan.md §34, §73, §75.3, Phase 15](../plan.md#73-master-plan--product-vision)

## Context

The master plan requires "native AI" while principles 12 (AI optional) and 15
(no mandatory cloud) forbid accounts and lock-in. Capabilities needed:
handwriting recognition, OCR, embeddings, chat/summarization, transcription,
equation solving, extraction. Providers vary wildly: on-device ONNX/NNAPI
models, Google ML Kit, desktop-native engines, and cloud APIs — each with
different latency, privacy, and availability characteristics.

## Decision

Define a **provider-abstracted `AiProvider` interface** in `core-ai` and route
every AI feature through it. No feature may call a model directly.

```kotlin
interface AiProvider {
  val id: String
  val capabilities: Set<AiCapability>   // HANDWRITING, OCR, EMBED, CHAT,
                                        // TRANSCRIBE, EQUATION, EXTRACT
  suspend fun recognizeHandwriting(input: StrokeGroup): HandwritingResult
  suspend fun embed(text: String): FloatArray
  suspend fun chat(request: ChatRequest): ChatResponse
  suspend fun transcribe(audio: AudioRef): Transcript
  // ...
}
```

Two provider families ship:

```text
local  — ONNX Runtime (NNAPI on Android, CPU/GPU on desktop); embeddings,
         handwriting recognition, OCR; opt-in model downloads with size budgets
byok   — OpenRouter gateway using the user's own API key; big-model chat,
         high-quality transcription, equations
```

Selection rules: prefer local for private/frequent data (handwriting, OCR,
embeddings); use BYOK for heavy generation when the user has enabled it. AI
features degrade gracefully when no provider is available (principle 12).

## Consequences

### Positive

- Zero vendor lock-in; models and providers are swappable configuration.
- Privacy control is architectural, not a policy: local is the default.
- A feature written once runs on both platforms and with any provider.

### Negative

- Interface design must anticipate capability sets that do not exist yet
  (over- or under-abstracting are both risks).
- Two provider families means two integration and testing surfaces.

### Neutral

- Agents (Phase 15) consume the same interfaces, so agent tools stay
  provider-agnostic; plugins can register additional providers.
